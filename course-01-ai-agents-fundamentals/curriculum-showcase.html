Course promise

A practical working model—not another product tour

In 52 minutes, learners replace vague, product-driven notions of AI with a practical working model of assistants and agents. They set up an off-the-shelf assistant on macOS, learn a reliable method for assigning work, and complete one small supervised workflow.

A concise, non-technical introduction for entrepreneurs and business users who have tried chat-based AI but still lack a dependable way to use it for real work. By the end: one AI assistant, one ordinary project folder, one repeatable way to delegate, one set of safety rules, and one completed supervised workflow.

Learner transformation

From scattered chats to a supervised working loop

Before

  • Treats every AI product as if it were “the model.”
  • Uses chat as disconnected questions.
  • Assumes the assistant remembers everything permanently.
  • Judges answers by polish or confidence, not evidence.
  • Unsure what an agent may read, change, or publish.

After

  • Separates model, product, assistant, and agent.
  • Chooses chat, skill, workflow, automation, or agent appropriately.
  • Gives clear assignments with sources, constraints, and success criteria.
  • Defines approval points before consequential actions.
  • Reviews work as the accountable owner of the outcome.

Learning outcomes

Four capabilities that define completion

  1. Explain the practical differences among a model, AI application, assistant, workflow, automation, and agent.
  2. Set up an off-the-shelf AI assistant on macOS and give it focused task context using ordinary files.
  3. Give, review, verify, and improve an AI assignment using explicit sources, constraints, deliverables, and success criteria.
  4. Complete a low-risk supervised workflow with appropriate permissions and human approval points.

For non-technical entrepreneurs, creators, coaches, independent professionals, and small-business teams. Prerequisites: a Mac, one supported AI assistant account, a practice folder, and one real but non-sensitive business task. No coding required. Not aimed at engineers building agent infrastructure—though the mental models remain useful.

    • 3

      Model, application, and assistant

      Explain why a model, an AI product, and an assistant are related but not interchangeable.

      • Runtime 4 min
      • Output One-sentence explanation of the distinction

      Key talking points

      • A model is the reasoning and generation engine—not the complete user experience.
      • The application adds interface, account, files, search, history, integrations, permissions, and product behavior.
      • An assistant is the working experience when model + instructions + context + capabilities combine.
      • Similar models can behave differently across products; one product may offer several models with different tradeoffs.
      • “Multimodal” means more than one form of information—not that every product supports every modality everywhere.

      Correct these

      • “ChatGPT” or “Claude” is simply one model.
      • A newer model automatically has more of the learner’s data.
      • Model intelligence and product permissions are the same capability.
      • A conversational tone means the system understands or cares like a person.

      Evaluate the complete system, not only the model name.

      Slide 2
      Capability comparison
      • Model capability vs. product capability vs. granted access
      • Example: summarizing vs. searching vs. saving
      Slide 3
      Changing the model ≠ changing the app
      • Speed, cost, reasoning, modality tradeoffs

      Glossary
      Model
      The reasoning and generation engine that analyzes and produces text (and sometimes other modalities)—not the full product experience.
      AI application / product
      The workplace around the model: interface, accounts, files, search, history, integrations, and permissions.
      Assistant
      The working experience created when a model is combined with instructions, context, product features, and available capabilities.
      Multimodal
      Able to work with more than one form of information (for example text, images, or audio)—subject to what the product actually exposes.

      Transition: An assistant can answer a request. An agent goes further by pursuing a goal across steps—but that is a spectrum, not magic.

    • 4

      Workflow, automation, or agent

      Choose the simplest appropriate working pattern and a suitable autonomy level.

      • Runtime 6 min
      • Output Autonomy level selected for the practice task

      Key talking points

      • A single response is not automatically a workflow or an agent.
      • A workflow is a sequence of steps—human, software, or AI.
      • An automation follows a predefined trigger and path when steps and exceptions are well understood.
      • An agent receives a goal, adapts some steps, uses tools, observes results, and continues within boundaries.
      • “Agentic” is a degree. More autonomy increases the need for trustworthy inputs, permissions, monitoring, and recovery.
      • Autonomy ladder: Suggest → Draft → Prepare → Act with approval → Act independently (course zone: levels 2–4).

      Correct these

      • Any chatbot with a friendly name is an agent.
      • An agent must operate without human involvement.
      • More steps or tools automatically make a system more usefully agentic.
      • Automation and agent are synonyms; the agent always knows when to stop.

      Earn autonomy through narrow scope, evidence, and successful review—not enthusiasm.

      What the model can see: prompts, instructions, and context

      Assemble focused context for a task without assuming that more information always produces a better result.

      • Runtime 6 min
      • Output Context checklist for the practice task

      Key talking points

      • A prompt is the immediate input; an assignment can include goal, sources, constraints, format, process, and success criteria.
      • Instructions stack: product rules, org/course rules, project rules, reusable skills, and the current request.
      • The model only uses what the application includes in the current model call.
      • A context window is finite working space; a large window is not perfect memory or perfect attention.
      • Relevance, authority, structure, and clarity beat filling the window.
      • Context checklist: outcome, audience, sources, constraints, example, deliverable, quality standard, what to ask rather than assume.

      Correct these

      • More context always produces a better answer.
      • A large context window is perfect memory.
      • Earlier chat messages are necessarily used correctly later.
      • The model can see every connected file at all times.
      • Prompting is mainly about finding a magical sentence.

      Give the smallest complete set of relevant, authoritative information.

      Prompt

    • 6

      Context, chat history, and memory

      Explain why current context, visible chat history, and persistent memory are not interchangeable.

      • Runtime 6 min
      • Output Classification of what the assistant has now, what may persist, and what must be supplied again

      Key talking points

      • Context = information available for the current task.
      • Chat history = visible prior messages; the product may not use every message every time.
      • Source knowledge = material deliberately supplied or selected for the task.
      • Memory = information a product preserves or retrieves later; behavior varies by product and setting.
      • Important business knowledge should not be assumed to persist because it appeared once in a conversation.
      • Advanced retrieval (RAG, embeddings, knowledge graphs) belongs in Course 2—name them only as a handoff.

      Correct these

      • A bigger model remembers the learner personally.
      • Chat history is reliable permanent memory.
      • The agent permanently learns every correction made in conversation.

      If information matters, know where it lives and deliberately provide or preserve it.

      Glossary
      Chat history
      A visible record of prior messages; visibility does not guarantee that every message is used in every response.
      Source knowledge
      Material deliberately supplied or selected for the task (briefs, notes, examples).
      Memory

      Tools, skills, and connections

      Distinguish reusable guidance from executable capability and from the connection mechanism.

      • Runtime 5 min
      • Output Capability map for the practice workflow

      Key talking points

      • Tools do—search, read, write, send, update, or otherwise act.
      • Skills guide—reusable instructions, procedures, examples, standards, and decision rules.
      • Connectors link the assistant to an external source or service; APIs define how systems exchange requests; MCP standardizes discovery and use for compatible clients.
      • A skill without a tool cannot perform the external action; a tool without a skill may be used inconsistently.
      • Connected ≠ selected ≠ correct. More tools increase action surface and risk.
      • Build a capability map from the workflow; grant the minimum needed per step.

      Correct these

      • A skill and a tool are the same thing.
      • MCP is the agent’s memory; MCP replaces APIs entirely.
      • Once a tool is connected, the agent will choose it correctly.
      • More tools always create a more capable system.

      Start from the workflow and grant the minimum capability needed for each step.

      An executable capability: search, read, calculate, write, send, update, or another action.

    • 8

      Permissions, boundaries, and approval

      Define least-privilege access and a human approval point for consequential work.

      • Runtime 3 min
      • Output One written stop-and-ask rule

      Key talking points

      • Read, create, edit, delete, send, publish, purchase, and administer are different permission levels.
      • Grant only the access needed for the current workflow; prefer reversible actions.
      • Instructions are guidance; technical permissions, scoped credentials, sandboxes, and approval UIs enforce limits.
      • A sandbox limits where actions can have effect—it does not make every output correct or harmless.
      • Prompt injection: untrusted content trying to redirect the agent—treat external pages and tool results as data, not authority.
      • Approve actions with legal, financial, reputational, privacy, or irreversible consequences.

      Correct these

      • A system prompt or skill is a security boundary.
      • A sandbox proves the result is safe.
      • Read-only access has no privacy implications.
      • Human review is unnecessary for a familiar recurring task.

      Instructions guide behavior; permissions limit consequences.

      Draft slides
      Slide 1
      Permission ladder

      • Least privilege for this workflow
      Slide 2
      Instructions vs. enforcement
      • “Please don’t publish” vs. no publishing permission
      • Prefer reversible: draft before send
      Slide 3
      Prompt injection (calm example)
      • External content is data, not authority over your goal
      • Don’t dramatize; do make the habit stick
      Slide 4
      Write your stop-and-ask rule
      • “Stop and ask me before ___.”

      Glossary
      Least privilege
      Granting only the access needed for the current workflow—nothing extra “just in case.”
      Sandbox
      An environment that limits where actions can have effect; it does not guarantee correct or harmless outputs.
      Prompt injection
      Untrusted content (pages, documents, emails, tool results) that tries to redirect the agent away from your goal.
      Stop-and-ask rule
      A written checkpoint: the agent must pause and get human approval before a named consequential action.

      Give a clear assignment with CLEAR

      Turn a vague request into an executable and reviewable assignment.

      • Runtime 6 min
      • Output One complete CLEAR assignment for the practice task

      Key talking points

      • Clarify the outcome—what, for whom, and why.
      • Load the context—facts, sources, history, examples; label authority.
      • Explain standards and constraints—hard constraints vs. preferences.
      • Ask for a deliverable—format, process, and stopping condition.
      • Review and refine—how you will inspect, verify, correct, and approve.
      • CLEAR is a thinking checklist, not a rigid prompt formula. Ask for missing info or a short plan before costly actions when gaps matter.

      Correct these

      • Prompt quality is mainly about secret phrases.
      • Assigning a persona is enough to define a job.
      • Very long prompts are necessarily better.
      • You must answer every possible question in advance; the first output is finished.

      A good assignment makes the outcome and the review standard visible.

      CLEAR method
      Clarify outcome, Load context, Explain standards, Ask for a deliverable, Review and refine—a checklist for executable, reviewable assignments.
      Hard constraint

      Deliverable

    • 10

      Brief with sources, files, and examples

      Give the assistant a small, labeled source pack and prevent silent assumptions.

      • Runtime 3 min
      • Output Source pack with authority labels and an ask-before-assuming rule

      Key talking points

      • Name the source of truth explicitly—do not make the agent guess which file is current.
      • Distinguish instructions from evidence; useful information is not automatic authority over the task.
      • Label files: approved, reference-only, draft, outdated, or archived.
      • Provide one or two strong examples and say what to imitate.
      • Tell the assistant how to handle conflicts; ask for citations when factual traceability matters.
      • Surface missing, conflicting, or low-confidence information before drafting.

      Correct these

      • The newest-looking file is necessarily the approved file.
      • An example is automatically interpreted as intended.
      • The agent will notice every contradiction; citing a file proves the conclusion.

      Label authority; do not make the agent guess which source wins.

      A small set of deliberately chosen files or notes provided for a task, with clear labels.

    • 11

      Correct, verify, and improve

      Review an output with evidence and turn a correction into a reusable quality improvement.

      • Runtime 3 min
      • Output Revised artifact and one reusable quality check

      Key talking points

      • Separate factual correctness, instruction-following, quality, and preference—they need different feedback.
      • Diagnostic feedback: issue → evidence → standard → requested correction → verification.
      • Verify claims against primary or authoritative sources when accuracy matters.
      • Ask for assumptions, unresolved questions, or a compliance checklist.
      • Save durable corrections in the relevant instruction, skill, source note, or memory—not only in chat.
      • Not every dislike should become a permanent preference; confirm the lesson should apply again.

      Correct these

      • A confident answer is a verified answer.
      • Asking “Are you sure?” is a sufficient fact check.
      • Every correction should become long-term memory.
      • A longer self-critique automatically improves the result.

      Correct the system where the error originated, then test the correction.

      Draft slides
      Slide 1
      Four review dimensions
      • Facts · instructions · quality · preference
      • Different feedback for each
      Slide 2
      Unhelpful vs. diagnostic
      • “This is bad. Try again.”
      • Issue → evidence → standard → correction → verify
      Slide 3
      Worked correction
      • Weekly vs. monthly reporting claim example
      • Scan for other unsupported service details
      Slide 4
      Task fix vs. system fix
      • One-off correction vs. durable instruction/skill/source

      Glossary
      Diagnostic feedback
      Feedback that names the issue, shows evidence, restates the standard, requests a specific correction, and verifies the fix.
      Verification
      Checking claims or requirements against an authoritative source or explicit standard—not asking the model if it feels sure.
      Reusable quality check
      A lightweight checklist or rule you keep for recurring work after a correction proves durable.

      From brief to reviewed output

      Execute the complete supervised loop once—from CLEAR assignment through verification and approval.

      • Runtime 2 min
      • Output One reviewed artifact through the complete supervised loop

      Key talking points

      • Keep the artifact deliberately small so the full loop is visible.
      • Workflow: open task → load sources → CLEAR assignment → confirm tools/permissions → plan or missing-info check → generate → verify → diagnostic revision → approve or reject.
      • Narrate human decisions: source authority, permission, verification, final approval.
      • Suggested demo: three article angles from a one-page brief; review for source support and unsupported claims; revise one angle.
      • Do not make the demonstration about a perfect first draft.

      Correct these

      • A successful demo means the workflow is ready for unattended use.
      • The entire conversation should be saved because every intermediate thought may be useful later.
      • The best workflow is the one that produces the largest artifact.

      The value is not the first answer; it is the controlled loop from context to action to verified result.
