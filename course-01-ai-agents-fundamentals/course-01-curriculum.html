Course promise

A practical working model, not another product tour

In about an hour, you replace vague product folklore with a working model of assistants and agents: what the model does, what the harness adds, how context and memory work, how tools and skills differ, and how to supervise one small workflow end to end.

Built for entrepreneurs and business users who have tried chat AI but still lack a dependable way to use it for real work. By the end you have Claude Desktop running, a workspace folder, ALIVE for memory across sessions, a CLEAR way to assign work, clear data-sharing rules, and one completed supervised loop, plus an honest view of where a single-user, file-based setup stops. Lessons are short enough to watch alone (about 2–6 minutes) or in sequence.

Learner transformation

From scattered chats to a supervised working loop

Before

  • Treats every AI product as if it were "the model," ignoring the harness/app around it.
  • Uses chat as disconnected questions, without seeing the tool/context loop.
  • Assumes the assistant remembers everything permanently.
  • Shares files or context with an AI product without knowing where that information actually goes.
  • Judges answers by polish or confidence, not evidence.
  • Unsure what an agent may read, change, or publish.

After

  • Separates model, product/harness, assistant, and agent.
  • Chooses chat, skill, workflow, automation, or agent appropriately.
  • Knows the practical difference between a local model and a cloud API, and what that means for sensitive information.
  • Gives clear assignments with sources, constraints, and success criteria, and installs a new skill deliberately when one is genuinely useful.
  • Defines approval points before consequential actions.
  • Reviews work as the accountable owner of the outcome, and knows when a file-based, single-user setup stops being enough.

Learning outcomes

What "done" looks like

  1. Explain the practical differences among a model, AI application (harness), assistant, workflow, automation, and agent, and how a modern chat turn actually runs.
  2. Set up Claude Desktop on macOS, extend the assistant with a new skill, and give it focused task context using ordinary files.
  3. Explain what gets shared with whom, including the practical difference between a locally-running model and a cloud API, well enough to make deliberate, cautious choices about sensitive information.
  4. Explain why an assistant has no persistent memory by default, what retrieval-augmented generation (RAG) does, and set up ALIVE for basic local memory across sessions.
  5. Give, review, verify, and improve an AI assignment using explicit sources, constraints, deliverables, and success criteria.
  6. Complete a low-risk supervised workflow with appropriate permissions and human approval points, and explain why a file-based, single-user setup is a different problem from a shared team setup.

For non-technical entrepreneurs, creators, coaches, independent professionals, and small-business teams. Prerequisites: a Mac, one supported AI assistant account, a workspace folder (project or Personal OS), and one real but non-sensitive business task. No coding required. Not aimed at engineers building agent infrastructure, though the mental models remain useful.

Presenter guidelines

Keep the hour coherent, current, and supervised

Before presenting

  • Treat this curriculum and course-01-slides.html as a paired source of truth. The slide file controls audience-facing sequence, copy, visuals, links, and embedded notes; this file controls teaching intent, objectives, misconceptions, demonstrations, and transitions. Reconcile both whenever one changes.
  • Preflight Claude Desktop (Lesson 3), Claude Code for plugin lessons, Python 3.10+, ALIVE, the workspace folder, links, permissions, and the fresh-session check. Keep a prepared installed state or short capture available for network-dependent steps.
  • Verify product commands, plan terms, and privacy settings against current official sources immediately before recording. State the date checked when showing policy or settings pages.
  • Use one public, non-sensitive practice task throughout. Reset its files to a known baseline before each take.
  • Do not record Lesson 10 until [Skill Name TBD] has been replaced with a real, reviewed skill and the corresponding slide copy and notes have been updated.

While presenting

  • The listed runtime includes the demonstration. Pre-stage setup and show only the decision or action that teaches the lesson; do not make viewers wait through downloads, authentication, or long generation.
  • The default slide URL shows the full-course cut. Add ?extended=1 for reinforcement slides, ?lesson-dividers=1 for standalone-clip title cards, or both for the complete reference deck.
  • Use each lesson divider to state the question or outcome. On content slides, explain the visual and add the example or caveat from this guide instead of reading the bullets aloud.
  • Narrate the human decisions: source authority, workspace boundary, permission, verification, correction, and approval. A successful demo is evidence of a supervised step, not proof that the system is safe for unattended work.
  • When a live step fails, name the failure, switch to the prepared state, and continue with a plain verify step (open it, try a simple prompt). Never imply that a skipped or simulated action succeeded live.
  • Use "local" precisely: ALIVE's files are local, while Claude Code model inference is cloud-based. Connected tools, sync, or telemetry can still transmit data even when a model runs locally.

      How models and harnesses work

      A model predicts the next tokens. It does not "think like a person." Named families help you spot category differences; the harness is the app around the model. Here's how one chat turn actually runs before you install anything.

      • Runtime 5 min
      • Output One-sentence model vs harness distinction, plus a sketched chat turn
      • Standalone clip Works alone, no setup required; uses diagrams, not your install.

      The most common misconception is that "the AI" is just the model. Install goes better, and safer when learners already know what the model does, what the harness adds, and how a chat turn with tools actually runs. Theory first; Claude Desktop install is Lesson 3.

      Key talking points

      • What a model does: A language model predicts likely next tokens and generates text (and sometimes other modalities). It does not open files, click buttons, or enforce permissions by itself, and a fluent reply is not the same as human understanding.
      • Named model families (as of recording): Name a few concrete families so learners can categorize, not memorize a catalog: e.g. Claude (Anthropic), GPT (OpenAI), Gemini (Google), and open-weight options you can run or host yourself. Teaching point: same category (models), different providers and tradeoffs; products change. Use "as of recording."
      • Harness / app / assistant vs model: The harness is ordinary software around the model: UI, context assembly, tool execution, history, and permissions. An assistant is the working experience when model + harness + instructions + context + capabilities combine. Claude Desktop is the harness we install in this course: the Mac app with files, tools, and permissions around the model. Claude Code (terminal) is the same product family for advanced use later; we start with the desktop app so beginners never need the command line.
      • One chat turn: You send a message → the harness assembles context → the model replies with text and/or tool requests → the harness runs allowed tools and feeds results back → the model may continue → you see a response (often with a step trail). Same model, different harness → different behavior.
      • Bridge: Next lesson we install and open that harness on your Mac, so the vocabulary has somewhere to land.

      Correct these

      • "ChatGPT" or "Claude" is simply one model.
      • The model itself executes tools, searches the web, or edits files.
      • A conversational tone means the system understands or cares like a person.
      • A newer model automatically has more of the learner's data or better permissions.
      • Model intelligence and product permissions are the same capability.

      Judge the model plus its harness, not the model name alone. Next: install the harness.

      Chat assistant, workflow, or agent?

      Three patterns on a spectrum: chat assistant, workflow, and agent. Learn the definitions, then try both sides in Claude Desktop: Chat for one reply, Code to change a file in your workspace.

      • Runtime 3 min
      • Output Chat vs Code exercise completed; learner can say who controlled each step

      Key talking points

      • Chat assistant: you ask, it replies. One turn at a time; no multi-step goal pursuit. A single reply is one chat turn (Lesson 2), not an agent.
      • Workflow: fixed steps you or rules control. A checklist or automation; each step defined in order.
      • Agent: you give a goal; the system chains steps and uses tools toward it, within boundaries set by the harness (with your approval).
      • Pick the simplest pattern that still saves time. You stay accountable for review before anything goes out.
      • In Claude Desktop, Chat gives one reply without changing your files. Code can take multiple steps on your workspace folder when you approve them. That is the practical difference between a chat assistant and agent-like work. (Chat may be labeled Home.)

      Correct these

      • Any chatbot with a friendly name is an agent.
      • An agent must operate without human involvement.
      • More steps or tools automatically mean you need an agent.
      • Workflow and agent mean the same thing.

      Pick the simplest pattern that fits your task. You stay in charge of what goes out.

      What your agent can actually see

      The model only sees what the harness puts in front of it this turn, not your whole disk, not every past chat. Here's how to assemble focused context.

      • Runtime 4 min
      • Output Context checklist for the practice task
      • Standalone clip Partial: context window concept stands alone; checklist ties to the practice task.

      Key talking points

      • A prompt is the immediate input; an assignment can include goal, sources, constraints, format, process, and success criteria.
      • Instructions stack: product rules, org/course rules, project rules, reusable skills, and the current request.
      • The model only uses what the harness includes in the current model call: it cannot "see" your whole disk or every past chat by itself.
      • The context window is everything the model can read in one request: instructions, history, files, tool results, and your message, all counted in tokens up to a hard limit.
      • When the window fills, older content drops off or gets summarized; the model cannot see what fell out. A large window is still not perfect memory.
      • Relevance, authority, structure, and clarity beat filling the window.
      • Context checklist: outcome, audience, sources, constraints, example, deliverable, quality standard, what to ask rather than assume.

      Correct these

      • More context always produces a better answer.
      • A large context window is perfect memory.
      • Earlier chat messages are necessarily used correctly later.
      • The model can see every connected file at all times.
      • Prompting is mainly about finding a magical sentence.

      Give the smallest complete set of relevant, authoritative information.

      Why your agent forgets everything

      The model has no built-in memory of the last chat; a new session only knows what the harness deliberately reloads. Here's why, and what chat history is not.

      • Runtime 4 min
      • Output Classification of what persists today vs what must be supplied again
      • Standalone clip Works alone: the most shared misconception in AI; no prior setup required.

      The single most consequential misunderstanding: people assume an assistant remembers them like a colleague. By default, it does not. The next lesson covers one common workaround (RAG). Later, after tools and plugins are clear, you will install ALIVE as a practical local-memory plugin.

      Key talking points

      • Context = information available for the current task. Chat history = visible prior messages; the product may not use every message every time. Source knowledge = material deliberately supplied. Memory = information a product preserves and retrieves later.
      • Chats and projects are isolated by default. What you said in one thread or workspace does not carry into another unless you deliberately connect them.
      • Each model call is stateless: it only sees what the harness puts in the current context window. Inside one chat thread, that usually means the full conversation so far is resent with every message you send.
      • Resent thread history is not persistent memory. A new session starts empty unless the product reloads history, files, retrieval, or a memory layer.
      • Important business knowledge should not be assumed to persist because it was said once. If it matters later, save it to a file, note, or memory plugin (ALIVE comes later in this course).

      Correct these

      • A bigger or newer model remembers the learner personally.
      • Another chat or project automatically knows what you discussed elsewhere.
      • Chat history is reliable permanent memory.
      • The agent permanently learns every correction made in conversation.

      No memory is the default. If information matters, know where it lives, or build a place for it.

      What RAG actually means

      Models can hallucinate plausible but wrong answers. RAG is a grounding technique: before answering, systems search your notes and pull relevant pieces into context. It helps, but doesn't guarantee truth.

      • Runtime 3 min
      • Output One-sentence explanation of RAG and its limits
      • Standalone clip Works alone: defines RAG without requiring ALIVE or any specific product.

      Key talking points

      • Without sources, models can sound confident while inventing plausible but wrong answers — that is hallucination.
      • RAG (retrieval-augmented generation) is a grounding technique: before generating, the harness searches notes or documents, pulls relevant pieces into context, then the model generates.
      • Grounding ties the answer to real source material instead of generation alone; it reduces invention but does not guarantee correctness or faithful use.
      • The model still only sees what was retrieved that turn: it did not "remember" on its own.
      • RAG is not memory: retrieval is one turn's context assembly; memory preserves information across sessions.

      Correct these

      • RAG is the same thing as memory.
      • RAG prevents hallucinations entirely.
      • RAG proves the retrieved answer is correct.

      RAG retrieves, then generates. Grounding reduces hallucination; it is not proof.
